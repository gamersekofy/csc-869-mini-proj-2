# Show-and-tell checklist

The professor's list, in his order, with the exact file and line to open and the one sentence to say
while it's on screen. Line numbers are current as of the commit this file ships in.

Have these open as tabs before you start: `components/mp2-py/csc869/sampling.py`,
`cv.py`, `models.py`, `metrics.py`, `error_analysis.py`, `results/feature_importance_grouped.csv`,
and a terminal at the repo root. Close everything else.

---

## 1 · Where imbalanced data is handled

**Open:** `components/mp2-py/csc869/sampling.py:18` (`resample_indices`), then `cv.py:62`.

> "Resampling lives in its own module and it returns row *positions*, not copied data. The call site is
> the important part: it's applied to the training slice of one fold, before preprocessing, and never to
> the validation fold or the test set. Downsampling and upsampling are the same function with a different
> target count."

If he asks where the three scenarios are defined: `sampling.py:16` (`SCENARIOS`) and
`components/mp2-py/configs/main.yaml`. If he asks why not SMOTE: Python-only, and the two-language
comparison is the spine — it's listed as future work, not quietly dropped.

**Proof it happened, in numbers:** `results/cv_runs.csv` has `n_train` per fold — 26,031 for `none`,
49,440 for upsampling, 15,682 for downsampling.

---

## 2 · Where the classifiers are applied

**Open:** `models.py:76` (`build_model`) then `cv.py:87` (the `fit_model` call inside the fold loop).

> "One builder function, five branches: decision tree, random forest, logistic regression, an RBF SVM, and
> kNN. Two of the five are wrapped in a scaler pipeline because they need it. The fold loop doesn't know
> which model it's fitting — it calls `fit_model` and gets back a fitted estimator plus timing metadata."

The depth tuning is `models.py:167`, called from `models.py:230`, evaluated on an inner 3-fold split so
the outer fold never sees it. Test-set refit is `test_eval.py:25`.

---

## 3 · Where ROC (and the other metrics) are implemented

**Open:** `metrics.py:79` (`roc_auc_score`), then `metrics.py:61` (rank averaging), then `curves.py:61`.

> "The metrics are written from scratch — the ROC curve is rank-based, Mann–Whitney, with average ranks for
> ties, and PR-AUC is the step-wise average precision, not a trapezoid. The plotting side just reads the
> per-fold curve points that `cv.py` exports and adds a ±1 SD band across folds."

- `metrics.py:55` F1, `metrics.py:95` precision-recall curve, `metrics.py:136` average precision.
- Curve grid: `cv.py:39` `_curve_points` (200 points, shared by all models and folds).
- Figures: `curves.py:61` ROC/PR, `curves.py:118` learning curves, `curves.py:176` the 5×3 heatmap.

## 4 · Feature importance analysis

**Open:** `results/feature_importance_grouped.csv`, then the figure `reports/figures/feature_importance.png`.

> "Gini importance from both tree models, fitted on the full training set with no resampling, and I summed
> the one-hot columns back to their source attribute so it's readable.
>
> For the random forest it's fnlwgt at 0.163, then age 0.152, marital-status 0.098, capital-gain 0.094.
> The single tree leans harder on marital-status alone, 0.198, then fnlwgt and education-num.
>
> And fnlwgt being at the top is worth being honest about: it's the census sampling weight, not a property
> of the person, so a tree using it is using a pseudo-identifier. Impurity importance flatters
> high-cardinality columns, which is exactly what that looks like. Dropping fnlwgt and checking with
> permutation importance is the first thing I'd fix."

Generated by `tools/feature_importance.py`; per-column detail is in `results/feature_importance.csv`,
grouped in `results/feature_importance_grouped.csv`, figure at `reports/figures/feature_importance.png`.

If he pushes on method: impurity importance is biased toward high-cardinality and correlated features;
permutation importance on the held-out folds is the honest version, and it isn't done here. Owning that
is better than defending the number.

## 5 · Live demo

**Terminal, repo root:**

```bash
cargo run --release
```

Full matrix, about **12 minutes 44 seconds** — too slow to sit through live. Two options:

- If he wants to see it *run*: let it go for 60–90 seconds while you narrate the lines (scenario / fold /
  model, F1, seconds), then Ctrl-C. Outputs are written per stage, so nothing is corrupted.
- If he wants to see it *finish*: `cargo run --release -- --quick` → **21 seconds**, 30 fits, and it still
  writes `cv_tidy.csv`, `cv_summary.csv`, `test_metrics.csv` into `results_quick/`-style output.

Python side, three commands, about 15 seconds total:

```bash
cd components/mp2-py
python -m csc869.run --list-stages
python -m csc869.run --stages curves --jobs 4
```

## 6 · Error analysis from the live run

The Rust binary does not do the error analysis — the Venn, agreement matrix and FP/FN split are Python-stage
outputs. So: after the run, regenerate them in three seconds rather than pretending.

```bash
cd components/mp2-py
python -m csc869.run --stages error --jobs 4
```

**Open:** `results/error_sample_ids.csv`, then the figures.

> "A fixed sample of 200 test records, 100 per class, drawn once with a seed. All three model families are
> wrong on 22 of them, at least one family is wrong on 50, and kNN is alone-wrong on 11 — those are the
> records nothing else misses. And the errors concentrate at education-num 9 to 13, which is 88–91% of the
> all-wrong cases depending on scenario."

If he wants to see it in the data rather than the figure: `results/hard_cases.csv` lists the records.
